## 2. SAST (static application security testing)

| Tool | Config | Gate |
|---|---|---|
| **Semgrep** (OSS) | Rulesets `p/typescript`, `p/react`, `p/nextjs`, `p/secrets`, `p/owasp-top-ten`, plus **custom rules** below | Block on ERROR |
| ESLint | Fix the config to ignore `.agents/`, `.opencode/`, `.next/`; add `eslint-plugin-security`, `no-restricted-imports` (the single enforcement point for the ADR-005 service-role allow-list; erratum 2026-11-10, C20) | Block on error |
| TypeScript | `tsc --noEmit` (passes today) | Block |
| Supabase DB lint | `supabase db lint` (splinter) on local DB | Block on `security` lints |

**Custom Semgrep rules (to write):**
1. `server-action-override-param`: in files with `"use server"`, an exported function parameter named `/.*Override$|actorSession/` or typed `SupabaseClient`. (SEC-01/02)
2. ~~`admin-client-outside-allowlist`~~ **Dropped.** The service-role allow-list is ADR-005's list (`lib/jobs/**`, `features/*/system.ts`, `app/api/{jobs,webhooks}/**`, behind one `getSystemDb(reason)` factory), and it is enforced by **one** mechanism only: ESLint `no-restricted-imports` (roadmap P1-34). `/api/v1` moves under RLS (ADR-011, amended), so it is no longer an allowed service-role path. (erratum 2026-11-10, C20)
3. `admin-query-without-tenant`: `$ADMIN.from($T).select(...)` chains with no `.eq("tenant_id", …)` in service-role modules. (SEC-05)
4. `postgrest-or-interpolation`: `.or(\`…${$X}…\`)` where `$X` comes from request params or body. (SEC-20)
5. `webhook-auth-return-true`: unconditional `return true` in `verify*Signature` functions. (SEC-04)
6. `env-gate-node-env-only`: security-sensitive branches gated solely on `process.env.NODE_ENV`. (SEC-14/15)
7. `console-log-pii`: `console.(log|info)` with identifiers named `phone|recipient|params|patient`. (SEC-15)
8. `fetch-follow-redirect`: `fetch(` in `lib/webhooks/**` without `redirect: "manual"`. (SEC-10)
9. `dangerously-set-inner-html` (guard against regressions).

## 4. Secret scanning

- **gitleaks** (`gitleaks detect --redact` over the full history; `gitleaks protect --staged` as a pre-commit hook).
  - Allow-list: the fake `clq_live_` literal in `tests/api/v1-auth.spec.ts:100` (or replace it with a runtime-generated value) (SEC-28).
  - Custom rules: `clq_live_[a-f0-9]{48}`, `whsec_[a-f0-9]{48}`, Supabase PAT `sbp_…`, MSG91 auth-key pattern.
- GitHub secret scanning + push protection, if the repo is on GitHub.
- **Never** run scanners in modes that upload repository content to third-party services without approval.
- Workstation hygiene check (owner): confirm `.env`, `.planning/dev-*.txt` are not synced to cloud drives; purge per SEC-15.

## 5. Server Action surface verification (local only)

Goal: confirm or refute SEC-01/02 dynamically and guard against regressions.
1. `next build` locally. Extract the action ID manifest (`.next/server/server-reference-manifest.json`) and map IDs → exported function names.
2. For every action: send a `POST /` with header `Next-Action: <id>` and an argument array that includes a forged `sessionOverride` and `clientOverride`, (a) with no cookies, (b) with a receptionist cookie from tenant A targeting tenant B.
3. Expected after the fix: every call returns an auth error, or ignores the extra args and acts as the real caller. Record results in a matrix.
4. Add an automated test that the manifest contains **no** action whose TypeScript signature includes override parameters (AST check via `ts-morph`).

### 6.2 Server Actions & route handlers: role × operation

Test IDs (selected):
- **TC-SA-01..06** (SEC-01): `searchPatients`, `getPatient`, `getPatients`, `updateClinicSettings`, `updateStatutorySettings`, `toggleGlobalConsent` with forged session args, both unauthenticated and cross-tenant → rejected.
- **TC-SA-10..** (SEC-02): each doctor-only action (`completeAndSignConsultation`, `addPrescriptionItem`, `finalizeVisitAmendment`, …) as receptionist and nurse → `PermissionDeniedError`. Each `clinic:manage` action as doctor → denied.
- **TC-SA-30**: `signed_by`/`created_by` always equal the session user.
- **TC-RLS-MEM-01..05** (SEC-03/08): self role change; admin → owner; last-owner demotion; invite owner as admin; consuming an invite with a different email.
- **TC-STAFF-01..04** (SEC-07): remove staff → session revoked, API keys revoked, invites revoked, PostgREST returns 0 rows.
- **TC-TOK-01..06** (SEC-05/22): cross-tenant token insert rejected; resolver tenant binding; resource_type mismatch → 404; expired/revoked → 410; reschedule token single-use; prescription token on `/api/reschedule` → 404.
- **TC-WH-01..07** (SEC-04/19): `dev`/unknown provider in production mode → 403; MSG91 without secret → 403; secret in query only → 403; replayed event → no-op; no cross-tenant phone fallback; response contains no tokens; `.or` injection in `replyMsgId` has no effect.
- **TC-API-01..10**: `/api/v1/*` with tenant A key against tenant B IDs → 404; revoked key → 401; creator-removed key → 401; scope enforcement (after P2-2); rate limit across two app instances (shared store).
- **TC-AI-01..06** (SEC-16): unauthenticated → 401; nurse calling clinical copilot → 403; injected `system`/`tool` messages dropped; tool outputs contain no 10-digit phone numbers; free text scrubbed before the provider call (assert via the mock provider capturing the payload); RLS-bounded results only.
- **TC-HDR-01** (SEC-13): headers present on `/`, `/patients`, `/r/x`, `/api/v1/patients`.
- **TC-RED-01** (SEC-17): callback `next` variants → same-origin only.
- **TC-UPL-01..03** (SEC-23): spoofed MIME rejected; object key has no patient name; oversize rejected cleanly.
- **TC-SSRF-01..05** (SEC-10): 302 → metadata IP, DNS rebinding (mock resolver), `0:0:0:0:0:0:0:1`, `64:ff9b::7f00:1`, decimal-encoded IPv4 → all blocked.
- **TC-AUD-01..05** (SEC-29): each clinical read emits an audit event; forged actor impossible; metadata allow-list enforced (including the webhook path).
- **TC-DPDP-01..05** (SEC-30): erasure restricts visibility for non-owner roles; communication data purged; storage objects handled per policy; export restricted to `exports:create`; the export is audited.

### 6.3 E2E (Playwright, local)
- Role-based navigation: hidden UI is also server-denied (pair every hidden button with an API call attempt).
- Session: idle timeout, logout invalidates the server session, MFA challenge for owner actions (after P1-5).

## 7. DAST (dynamic application security testing), staging/local only

- **OWASP ZAP**: baseline scan (passive) on local and staging; authenticated full scan using a ZAP context with a receptionist session and a separate owner session; exclude `/api/webhooks/*` and cron routes from active attacks except dedicated tests; rate-limit the scanner.
- **API scan**: ZAP OpenAPI import from `/api/v1/openapi.json` against staging with a staging API key.
- **Nuclei** (optional): misconfiguration and exposure templates only, against staging.
- Do **not** run DAST against production, Supabase-hosted endpoints, MSG91 or AI providers.

## 8. Manual testing / penetration test

- Internal manual review of the post-fix code (repeat this assessment's checklist: every `getAdminClient`, every `"use server"` export, every public route, every SECURITY DEFINER function, every storage policy).
- **External penetration test** (CERT-In empanelled auditor recommended for Indian healthcare customers) after P1, scoped to: web app, `/api/v1`, Supabase RLS via direct PostgREST, storage, public token links, webhook endpoints, and AI prompt injection.
- Threat-model refresh at each major feature (ABDM integration, payments, patient portal).

## 10. CI pipeline (proposed order)

```
lint+tsc → semgrep (custom+community) → gitleaks → npm audit / osv-scanner →
unit tests → supabase start + migrations + db lint → RLS matrix + authZ/tenant suites →
next build → server-action manifest check → e2e (Playwright) → ZAP baseline (local server)
```
Nightly on staging: ZAP authenticated scan and API scan. Release gate: all suites green with no High/Critical.

## 11. Reporting
- Each run produces a machine-readable report (SARIF for Semgrep/gitleaks/OSV, JUnit for tests, ZAP JSON) stored as CI artefacts for at least 1 year (DPDP/CERT-In evidence ⚖).
- Findings go back into `SECURITY_ASSESSMENT.md` IDs with a status column (Open / Fixed / Verified / Risk-accepted).
