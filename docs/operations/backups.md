# ClinicQ Backup & Disaster Recovery Standard Operating Procedure

> **Status:** Active Operational Reference (Phase 1 Baseline)  
> **Authority:** `AGENTS.md` §9 (Sensitive Data), §14 (Database Rules), §46 (Production Readiness)  
> **Responsible Role:** Lead Operations Engineer / Clinic System Administrator

---

## 1. Overview & Architecture

ClinicQ relies on Supabase managed PostgreSQL infrastructure hosted in encrypted cloud regions. Data resilience is guaranteed at two layers:

1. **Daily Managed Backups:** Full database image snapshots captured daily and retained in durable, multi-region cloud object storage.
2. **Point-In-Time Recovery (PITR):** Continuous Write-Ahead Log (WAL) archiving that enables restoring the database state to any specific second within the retention window.

All database backups inherit the storage platform's AES-256 encryption at rest and TLS 1.3 encryption in transit. Backup archives contain all application tables, schemas, indexes, and Row Level Security policies.

## 3. Security, Encryption & Sensitive Data Handling

- **Encryption:** Backup volumes and WAL streams are encrypted with customer-isolated KMS keys.
- **Access Boundary:** Access to restore triggers and backup archives is restricted to the Supabase Organization Owner via Multi-Factor Authentication (MFA). Database credentials and service-role keys are never included in plaintext within backup reports.
- **Audit & Consent Records:** The immutable `audit_logs` and `consent_records` tables are included in every snapshot. They inherit the exact same data classification and access boundaries as clinical patient records.
- **Temporary Export Expiration:** Any patient data exports generated by clinic staff reside in ephemeral, private storage buckets configured with signed URLs that expire after 15 minutes. Temporary exports are never retained in permanent backup snapshots.

## 4. Disaster Recovery & Restore Procedures

### 4.1 Triggering a Point-in-Time Restore (PITR)

When recovering from data corruption or catastrophic operational error:

1. **Identify Recovery Target:** Determine the exact UTC timestamp immediately prior to the corrupting event using `audit_logs` timestamps.
2. **Access Supabase Dashboard:**
   - Navigate to `Database` > `Backups` > `Point in Time Recovery`.
3. **Initiate Restore:**
   - Select the target date and UTC time.
   - Choose whether to restore to a new clone project (recommended for non-destructive verification) or restore directly to the current project instance.
4. **DNS & Service Pointing:**
   - If restored to a new project instance, update the `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` environment variables in the deployment configuration (e.g. Vercel).
   - Trigger a zero-downtime redeployment.

### 4.2 Post-Restore Data Integrity Verification

Before reopening clinic traffic, operations must execute the automated verification protocol:

1. **Row Count Parity Check:**
   Run an inspection query across all tenant-owned tables to verify row counts match expectations:
   ```sql
   SELECT 'tenants' AS tbl, count(*) FROM public.tenants
   UNION ALL
   SELECT 'memberships', count(*) FROM public.memberships
   UNION ALL
   SELECT 'patients', count(*) FROM public.patients
   UNION ALL
   SELECT 'audit_logs', count(*) FROM public.audit_logs
   UNION ALL
   SELECT 'consent_records', count(*) FROM public.consent_records;
   ```
2. **Automated Tenant Isolation Verification:**
   Run the test suite against the restored endpoint:
   ```bash
   npm run test
   npx vitest run tests/security/cross-tenant.spec.ts
   ```
   All tests must pass with 0 failures to confirm RLS policies and table structures restored without degradation.
3. **Manual Health Check:**
   Verify clinic login via OTP and verify dashboard patient lookup loads under 200ms.

## 5. Regulatory & Compliance Notice

Treating patient and clinical data as sensitive by default is an engineering principle of ClinicQ. However, having technical backup procedures in place does not automatically constitute certified compliance with HIPAA, NABH, or ISO 27001. Formal regulatory compliance requires independent external auditing, business associate agreements (BAAs), and administrative controls outside this technical specification (`AGENTS.md` §9).
