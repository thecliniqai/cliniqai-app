## The CI failure in `loading-states.spec.ts` (coordinator item)

CI run 43705726084 at `bab829e` failed "the skeleton shows during a slow client navigation" for Live Queue and
Calendar on desktop-chrome (3 attempts each): `clickNavLink` used `page.getByRole("link", { name, exact: true })`,
which matched both the Sidebar link and Today's own "Live Queue" / "Calendar" links in `#main` (strict mode).

**Root cause of local-pass / CI-fail: a race, not data.** Today (`/`) streams: its `loading.tsx` skeleton shows first
and the page (with the two links) follows. The test clicked as soon as `<main>` was visible and the target's prefetch
had settled. Measured locally (a probe spec, removed): main visible at 184 ms with one matching link and the skeleton
on screen, prefetch settled at 294 ms (still one link), Today's content at 477 ms. On the busy shared local stack the
click always won the race; on CI's fresh stack Today rendered first, so two links matched. The links are not
data-dependent (Today renders them for every clinic).

**Fix.** `clickNavLink` scopes every locator to the shell navigation (the visible `navigation "Primary"`, or the More
sheet below 768 px). `loading-states` now waits for the source page's skeleton to go before the click, so the
two-link condition always holds. **Fails without:** with the wait and the old helper the local run fails exactly as CI
did (`evidence/06-09e/loading-states-fails-without.txt`: the same two tests, "strict mode violation … resolved to 2
elements"); with the fix it passes on every project of the PR lane (below), 0 retries.
