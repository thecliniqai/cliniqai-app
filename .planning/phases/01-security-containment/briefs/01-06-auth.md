## 3. Target minimal flows (AUTH-04a)

**Principle (AUTH §2.4):** `signInWithPassword`, `resetPasswordForEmail` and `verifyOtp` run **in the browser** through `lib/supabase/client.ts`, so per-IP limits see the user's IP. **No new Server Action** is needed, which avoids a new authn/tenant surface. E10 adds a constraint: these calls must never use a service-role-keyed client, because that bypasses CAPTCHA on `/token` and `/signup` once CAPTCHA is turned on.

**Suggested shape:** put the logic in a small client-safe module, e.g. `features/auth/password-flows.ts`, with pure functions that take a `SupabaseClient`: `signIn(client,{email,password})`, `requestReset(client,{email})` and `completeReset(client,{email,code,newPassword})`. They return `{ok}` or `{ok:false, code}`. Pages are thin wrappers around them. That lets Vitest test the real app code against the local stack without Playwright, which arrives in V2-02. Add `features/auth/schemas.ts` (zod: email; password at least 10 characters and at most 72 UTF-8 bytes, rejected with "Use at most 72 bytes…" per §5; 6-digit code). §4.2 places that file in `features/auth`.

### 3.1 `/login` (rewrite `app/(auth)/login/page.tsx`)
- Email and password form. Use `autocomplete="email"` and `autocomplete="current-password"`, a show-password toggle (§3.3), and a "Forgot password?" link to `/forgot-password`.
- No "Create account" link yet, because `/signup` arrives in V2-13b. Use neutral copy for new clinics, e.g. "New clinic? Contact us", or nothing. Ask the PO (§8 Q5).
- On success: `router.replace("/")` and `router.refresh()`. The existing layout redirects handle routing (§3.3 routing table is AUTH-07).
- Errors use **fixed strings, never `error.message`** (AD-7). This is a minimal inline map. The full `errors.ts` comes in AUTH-04b.

  | Supabase code | Message |
  |---|---|
  | `invalid_credentials` | "Email or password is incorrect" (the same for unknown users, E11) |
  | `email_not_confirmed` | the same generic message (not reachable locally while confirmations are off; avoids the enumeration leak in AD-7) |
  | `over_request_rate_limit` | "Too many attempts, please wait a minute" |
  | anything else | "Sign-in failed, try again" |
- Delete the OTP step, resend, `devOtpHint`, the social buttons, the "ABDM Ready" badge and the trust footer claims. `ClinicShowcasePanel` may stay; it gets restyled later.
- A normal login sends **0 emails** by construction: `/token` password grant only, with no `/otp`, `/magiclink` or `/recover` call.

### 3.2 `/forgot-password` (new: `app/(auth)/forgot-password/page.tsx`, two steps on one page per §3.4)
1. Email → `client.auth.resetPasswordForEmail(email)` with no `redirectTo` (code only, §2.3). Always show "If an account exists, we've sent a code". E8 confirms `/recover` returns an identical 200 `{}` for existing and missing users (1 email vs 0).
   - Map `over_email_send_rate_limit` to the same neutral message, or to "wait a minute". The per-user `max_frequency` gives a 429 on a second request inside the window (E9). Use a 60 s client cooldown on "resend code", which calls `resetPasswordForEmail` again.
2. Code, new password and confirmation. **Validate the password with zod before calling `verifyOtp`** so that a weak password does not burn the code and leave a stray session. Then:
   1. `verifyOtp({ email, token: code, type: 'recovery' })`. Pin `'recovery'`: E1 shows a recovery code also verifies as `'email'`/`'magiclink'`, so the server will not enforce the type for us.
   2. `updateUser({ password })`. No `current_password` is needed: A00-5 measured that recovery sessions are exempt even with the setting on.
   3. `signOut({ scope: 'others' })` (E6 confirms that `others` kills the other refresh tokens). No MFA step yet (AUTH-08).
   4. `router.replace("/")`.

   Error mapping:

   | Code | Message |
   |---|---|
   | `otp_expired` | "Code is wrong or expired" (E1 returns the same 403 for wrong, used and expired codes) |
   | `weak_password` | the policy message |
   | `same_password` | "Choose a different password" |

   - If `updateUser` fails after a successful verify, the user holds a valid recovery session (`amr: otp`, any age, A00-5). Keep them on the form to retry, and call `signOut({scope:'local'})` if they leave or cancel. Do not route them into the app with the old password unchanged. **This is a gap the docs do not address; record it as a known residual for V2-03 (A00-5 "consider a server-side age bound").**
- **Email template prerequisite (needs a decision).** The flow needs `{{ .Token }}` in the recovery email. The repo has **no** `[auth.email.template.recovery]` (the spike set templates only in a scratch copy), and the CLI default recovery template was **not** measured. The default may contain only `{{ .ConfirmationURL }}`, and that link would land on a deleted `/auth/callback` (PKCE `?code=`). Options:
  - (a) Add `supabase/templates/recovery.html` (code only) and `[auth.email.template.recovery] content_path` in `config.toml` now. This is small, but it touches config that AUTH-02 owns in V2-03.
  - (b) If Mailpit shows the default template already includes the code, change no config.

  Verify in Mailpit first. A pinned test asserts a 6-digit code exists in the message.
- **PKCE caveat.** The spike used plain supabase-js clients. The app's browser client is `@supabase/ssr` with the PKCE flow (the `code_verifier` is stored at `resetPasswordForEmail`). Tests must build the client with `flowType:'pkce'` (or the ssr browser client) to prove that `verifyOtp(recovery)` with a 6-digit token still returns a session under PKCE. This was **not measured in AUTH-00**.

## 5. New-clinic signup and staff join after OTP removal (this phase)

**New clinic owner: no self-service path from V2-01 until V2-13b.** The docs say so explicitly (roadmap :626, AUTH §9 phase order note). Owners and tenants come only from synthetic seeds.
- `/clinic/new` and the dashboard redirect to it (`layout.tsx:26`) stay as they are. AUTH-07 replaces them with `/onboarding/clinic`.
- In practice only a seeded user with no membership can reach `/clinic/new`. The AD-3 "unlimited clinics per user" residual remains until V2-13b.
- **Gap (A00-1/A00-2):** deleting app code does not close the Supabase API. With `enable_signup = true`, a direct `/otp` or `/signup` call still creates users (E2). A user created by `/signup` with confirmations off locally could sign in and create clinics. The hosted test project is unknown (OI-1). See Q1.

**Staff join: what the docs support.**
- AUTH §6 rewrites `/join` as "set-password **or** sign-in-to-accept".
- The set-password branch needs admin `createUser`/`updateUserById` in `features/auth/system.ts` plus the `consume_invitation_for` RPC. That is AUTH-06, in V2-05 (backend) and V2-11 (UI), so it is **not** in 01-06.
- The minimal behaviour that keeps working without OTP is §3.2's third branch, **"Invitee has a confirmed account → Sign in to accept"**:
  - `/join?token=…` renders only.
  - If there is no session, show "Sign in to accept this invitation" with a link to `/login`.
  - If signed in, an "Accept" button calls the existing `acceptInvite(token)`.
- **What breaks, explicitly:** someone **without an existing account cannot join** between V2-01 and AUTH-06 (V2-05 backend, V2-11 UI). New staff exist only through seeds or a manual admin create, and the invite link stays bound to no email (SEC-08 unchanged until AUTH-06).
- **Return-to-join after login (needs a decision):** without a safe `next` (AUTH-04b), login lands on `/` and loses the token. Two options:
  - (i) Pull forward the one-line validator `^/(?![/\\])` (§4.2) for `/login?next=` now, with its unit tests (`//evil`, `/\evil`, `@evil` → `/`).
  - (ii) Tell the user "after signing in, open the invite link again". The page reads the token from the URL each time.

  Option (ii) keeps AUTH-04b's scope intact. See Q4.

## 6. Tests to add (local stack + Mailpit; behavioural, no source greps)

Put the integration tests under `tests/integration/auth/` (AUTH §7). They use `seedTenantWithOwner` / `addMemberToTenant` (admin-created, confirmed, per-run password) and run-scoped `@example.test`-style synthetic addresses.

Use the Mailpit REST API at `http://127.0.0.1:54324`:
- **count per recipient** with `GET /api/v1/search?query=to:<addr>`, not the global total, so parallel files do not interfere;
- read the body with `GET /api/v1/message/{ID}`;
- extract `\b\d{6}\b`.
- Never print codes or passwords.

1. **Password sign-in, seeded users (acceptance).** For owner, doctor and receptionist seeded users, `signIn()` from `password-flows.ts` with a browser-equivalent anon PKCE client returns a session.
   - `amr[0].method === 'password'` (E7).
   - The user can read their own membership row through RLS.
   - A wrong password and an unknown email both return the same mapped code `invalid_credentials`.
2. **0 emails on a normal login (acceptance).** Record the Mailpit count for the user's address, sign in successfully, wait about 1-2 s (Mailpit ingest), and assert the count is unchanged (0 new). Also assert that a failed login sends 0.
3. **Forgot password sends exactly one email.** `requestReset()` for a seeded user gives exactly 1 new message to that address with a 6-digit code. `requestReset()` for an unknown address returns the same `{ok:true}` shape and 0 messages (E8 `/recover`).
4. **Recovery code sets a new password.** `completeReset({email, code, newPassword})`:
   - the session is established; the old password then gives `invalid_credentials`; the new password signs in;
   - reusing the code gives `otp_expired` (single-use, E1);
   - a second client signed in before the reset gets `refresh_token_not_found` on refresh (the `signOut({scope:'others'})` step, E6).
5. **Recovery negatives.**
   - A wrong code gives `otp_expired` and the password is unchanged.
   - A too-short or over-72-byte password is rejected by the schema **before** `verifyOtp`, so the code is still usable afterwards.
   - `same_password` is mapped.
   - Use a separate user per case to avoid the per-user `max_frequency` 429 (E9).
6. **Pin the PKCE behaviour** (§3.2 caveat): run tests 3-4 with the client in `flowType:'pkce'`. If it fails, that is a blocking finding for the plan, not something to work around.
7. **Unit (pure):** the `schemas.ts` boundaries (9/10 characters; 72 vs 73 bytes using multibyte characters); the minimal error map (every listed code goes to a fixed string, an unknown code goes to the generic string, and the output never contains the input `message`); the safe-`next` validator if Q4(i) is chosen.
8. **Join (minimal).** A DB test that `acceptInvite` works for a password-signed-in existing user. The existing `tests/auth/invite.spec.ts` already covers the RPC, so extend it only if `/join` logic moves into a testable function.
9. **Regression kept:** the moved §3 of dev-logger-lockout (no invite token in production).
10. **Lint gate fixture:** a fixture file showing the new `no-restricted-syntax` rule fires on `shouldCreateUser` (the same pattern as the ADR-0005 bypass fixtures), so the gate is proven by a tool and not by a grep test.

**Not testable in V2-01:**
- UI at 360 px, tablet and desktop, and axe (DoD 3), because there is no Playwright scaffold until V2-02 (P1-27). Record a manual 360/1280 check, or defer axe to V2-02 explicitly with PO consent.
- Rate-limit 429s (A00-4: the CLI stack enforces no per-IP limits).
