## Consensus Summary

### Critical Findings (Must Fix Before Execution)

1. **Provider Sender ID Resolution (Plan 01):** `Msg91Provider` currently looks for `process.env.MSG91_SENDER_ID`, while the environment specification and template sync tool use `MSG91_INTEGRATED_NUMBER`. Must resolve both: `options?.integratedNumber || process.env.MSG91_INTEGRATED_NUMBER || process.env.MSG91_SENDER_ID`.
2. **Caller Parameter Name Alignment (Plan 01):** Existing call sites pass parameter names that differ from template keys:
   - `appointment_rescheduled`: caller passes `new_date_time` (expected: `new_appointment_time`)
   - `lab_report_uploaded`: caller passes `document_title` (expected: `test_name`)
   - `referral_letter_issued`: caller passes `specialist_name` (expected: `referred_to_name`)
   - `appointment_cancelled`: caller passes `reason` (expected: `cancellation_reason`)
   - `consultation_documents`: caller passes `prescription_url` and `receipt_url` but no single `token` or `document_url`.
3. **DLR Failure Status Loop (Plan 02):** Marking permanent delivery failures as `failed` causes `dispatchPendingQueue` to immediately re-enqueue and retry them forever since `failed` in the current schema represents retryable errors. Permanent failures must transition to `dead_letter` or have `next_retry_at` set to NULL/far future.
4. **Notification Category DB Constraint (Plan 02):** Inserting delivery failure alerts with `category: "communication"` will trigger a PostgreSQL CHECK constraint violation (`000014:97` permits only `'clinical', 'queue', 'billing', 'system'`). Must use `'system'` or `'queue'`.
5. **Inbound Two-Way Cancellation Guard (Plan 02):** Cancellation with slot release must be restricted strictly to interactive quick-reply button IDs (`btn_cancel`) and never triggered by loose numeric/free-text matches (e.g. answering "2 days" to a question). Furthermore, appointment lookup must be tenant-scoped using message correlation (`replyMsgId` / `external_message_id`) rather than global `limit(1)` phone matching.
6. **Missing DB Index for DLR Lookup (Plan 01):** `communication_queue.external_message_id` is unindexed. Migration `000016` must add an index on `communication_queue(external_message_id)` for fast DLR webhook lookups.
7. **Template Sync Import Guard (Plan 03):** `scripts/msg91-sync-templates.ts` must guard `main()` with `if (process.argv[1] === fileURLToPath(import.meta.url))` so Vitest tests can import helper functions without auto-executing CLI network requests.

## 05.1-01

### Summary
Wave 1 correctly diagnoses the largest real defect in the codebase: `lib/messaging/providers/msg91.ts:104-133` builds a raw Meta-style `components` array and posts to `api.msg91.com`, which cannot match MSG91's `to_and_components` bulk contract. The migration/type work is right and small. However, the plan's mapping matrix is derived from the template JSON in isolation, not from how the seven existing callers actually populate `template_params`. Traced end-to-end, at least four of the 13 templates produce a defaulted or wrong variable in production, and one production-blocking config gap (`integrated_number`) is missing entirely.

### Strengths
- **Correct root-cause diagnosis.** `msg91.ts:96-134` uses `payload.to` + `template.components[{type:"body",parameters}]`; the plan replaces it with `to_and_components` + `body_n`, matching every caller's one-recipient pattern in `dispatcher.ts:169-176`.
- **Migration is genuinely needed and correctly numbered.** `000014_communications_and_ai.sql:23` constrains `status` to six values; `lib/db/types.ts:1255` mirrors it; `000015_visits_metadata.sql` already exists, so `000016` is free.
- **Test-first ordering** with Wave 0 before implementation matches `05.1-VALIDATION.md:54-58`, and the threat model (T-05.1-01/02) targets real failure modes (positional swap, empty params).
- **Sanitizer scope is well chosen** — Meta will reject empty/`\n` params, and the caller data is genuinely dirty (e.g. `features/appointments/actions.ts:112` passes `doctorName` that may be empty).
- **DevLogger reuse** is cheap and already exists (`lib/messaging/dev-logger.ts:62-95`), so the dev path needs no new code.

### Concerns
- **HIGH — `integrated_number` is read from the wrong env var.** `Msg91Provider` takes the sender from `MSG91_SENDER_ID` (`lib/messaging/providers/msg91.ts:15`), while `.env.example:14` and `scripts/msg91-sync-templates.ts:22` use `MSG91_INTEGRATED_NUMBER`. `lib/messaging/index.ts:35` constructs `new Msg91Provider()` with no options, so in production `integrated_number` is `""` and *every* WhatsApp send fails. The plan's Task 4 lists "Update endpoint domain" but never touches env resolution, and its test asserts `integrated_number: "919876540000"` by injectng `senderId` — so the test passes while production is broken.
- **HIGH — `consultation_documents` has no resolvable button token.** Template has one URL button `https://app.thecliniqai.com/r/{{1}}` (`whatsapp-templates.json`, `consultation_documents`), but the only caller passes `prescription_url` and `receipt_url` and **no** `document_url` (`features/billing/actions.ts:1250-1257`). The plan's alias set is `token ← url | share_url | link_url | token`, none of which match → `button_1` becomes the fallback `"-"`, yielding `https://app.thecliniqai.com/r/-` in a live patient message. The same template also documents two buttons in body copy ("prescription and receipt") while the approved template exposes one.
- **HIGH — alias table misses several real parameter names.** Traced callers vs. plan matrix:
  - `appointment_rescheduled`: caller sends `new_date_time` (`features/appointments/actions.ts:190`), plan maps `new_appointment_time` with no alias → `body_4 = "-"`.
  - `lab_report_uploaded`: caller sends `document_title` (`features/labs/actions.ts:522`), plan expects `test_name` with no alias → "your diagnostic report for - from …".
  - `referral_letter_issued`: caller sends `specialist_name` (`features/referrals/actions.ts:669`), plan expects `referred_to_name` → "referred you to -".
  - `appointment_cancelled`: caller sends `reason` (`features/appointments/actions.ts:282`), plan expects `cancellation_reason` → "Reason: -".
- **MEDIUM — `clinic_name` default is unspecified and will not be the clinic's name.** `features/appointments/actions.ts:110-114` and `features/visits/scheduling.ts:491-495` omit `clinic_name`; the plan says "from tenant config or `"Clinic"`" but `dispatcher.ts` has only `tenant_id` and no tenant name. A literal `"Clinic"` default breaks D-02's branding promise and contradicts the plan's own test expectation ("Pune Care Clinic"). Fetching the tenant name per dispatch also adds a query per message (N+1 across `dispatchPendingQueue`'s loop, `dispatcher.ts:144`).
- **MEDIUM — D-08 is asserted but not implemented, and the plan contradicts itself.** `getMessagingProvider` defaults to `"dev"` only when `MESSAGING_PROVIDER` is unset (`lib/messaging/index.ts:20-47`); with `MESSAGING_PROVIDER=msg91` (as in `.env.example:15`) and no auth key, the provider returns `{success:false, error:"MSG91_AUTH_KEY is not configured"}` (`msg91.ts:24-30`, `86-92`) — no fallback. `must_haves` says "DevLogger fallback activates when MSG91_AUTH_KEY is not configured", while Task 1 test #6 asserts the hard error. `lib/messaging/index.ts` is not in `files_modified`.
- **MEDIUM — `doctor_name` defaulting degrades patient-facing copy.** `prescription_ready` body reads "your digital prescription from Dr. {{2}}"; the only caller omits `doctor_name` (`features/prescriptions/actions.ts:776-780`), so patients receive "from Dr. Doctor". The "Doctor" fallback in `features/appointments/actions.ts:189` shows the same pattern already shipping.
- **MEDIUM — `staff_onboarding_otp` is mapped through `template-bulk`** even though D-01 defers OTP. MSG91/Meta authentication templates use an OTP-specific component contract; including it in the 13-template matrix creates a latent trap and inflates "all 13 templates must map" tests without a consumer.
- **MEDIUM — no index for the DLR lookup the plan's own Wave 2 depends on.** `000014` indexes only `(status,next_retry_at)` and `(tenant_id,created_at)` (`000014:35-40`). `external_message_id` has no index (`000014:28`). Wave 1 is the natural place to add it; the research even claims it exists ("indexed on `external_message_id`"), which is false.
- **LOW — migration has no down/rollback path and its "test" is `npm run typecheck`** (`05.1-VALIDATION.md:41`). Typecheck cannot detect a wrong constraint; AGENTS.md §14/§38 asks for migration verification.
- **LOW — `Object.values(params).join(" ")` as session-text fallback** leaks raw parameter names/values into user-visible text.

### Suggestions
1. Add `integratedNumber` resolution: `options?.integratedNumber || process.env.MSG91_INTEGRATED_NUMBER || process.env.MSG91_SENDER_ID`, and add a test that builds the provider via `getMessagingProvider("msg91")` with only `MSG91_INTEGRATED_NUMBER` set.
2. Build the alias table from a grep of `enqueueMessage(` call sites, not from the JSON; add `new_date_time`, `document_title`, `specialist_name`, `reason`, `prescription_url`. Add a compile-time-ish guard test that *invokes every caller shape* (fixture per template mirroring `features/*/actions.ts` params) rather than a hand-written ideal param object.
3. Fix `consultation_documents` at the source: have billing pass a single combined `document_url` (needs a `resource_type` for a combined visit view — `000014:141-142` currently allows only `patient_document|prescription|invoice|referral`), or change the template. Do not silently fall back to `"-"`: make `buildPositionalComponents` throw/skip-send on a missing required button token.
4. Resolve `clinic_name` (and `doctor_name`) at enqueue time in the callers, or fetch tenant/doctor names once per dispatch batch; don't default to `"Clinic"`/`"Doctor"`.
5. Decide D-08 explicitly: either implement key-based fallback in `lib/messaging/index.ts` (and add it to `files_modified`) or downgrade the `must_haves` line to what the code will do.
6. Add `create index concurrently ... on communication_queue (external_message_id)` to `000016`, plus a rollback comment block.

### Risk Assessment
**HIGH.** The provider rewrite is directionally correct and low-drama, but as written it will ship a broken `integrated_number` and multiple `"-"`/`"Dr. Doctor"` messages to real patients on first production send. These are one-line-to-fix issues that the plan's own ideal-param tests will not catch.

## 05.1-02

### Summary
Wave 2 is the highest-value and highest-risk plan. Its reuse of `cancelAppointment` is the right call — slot release and waitlist alerting already exist (`features/appointments/actions.ts:246-266`), so D-04 mostly needs a correct inbound path, not new domain logic. But the DLR half conflicts with the existing outbox state machine, one insert violates a DB CHECK constraint, and the inbound half amplifies a pre-existing cross-tenant phone-matching weakness into an action that cancels other clinics' appointments.

### Strengths
- **Correct DLR need and correct target.** `communication_queue.status` cannot accept `delivered`/`read` today (`000014:23`), and `external_message_id` is already persisted on send (`dispatcher.ts:198`), so correlation is possible with data that exists.
- **Route-level integration matches existing structure.** The handler already branches on provider, verifies signature first (`route.ts:19`), and already inserts Event #18 `inbound_whatsapp_reply` (`route.ts:200`), so D-05 is an extension rather than a rewrite.
- **Wave 0 integration tests mirror proven mocking style** — `tests/messaging/two-way-bot.spec.ts:92-178` shows the `NextRequest` + `vi.spyOn(appointmentsActions, ...)` pattern the new suite can reuse.
- **Cancellation path is genuinely idempotent-ish and auditable** — `cancelAppointment` writes `cancellation_reason` into `visits.metadata` (`features/appointments/actions.ts:230-235`) and the route adds an audit row.
- **Threat model calls out the right spoofing threat (T-05.1-04)** and extends signature verification in the right place (`lib/messaging/webhook-helpers.ts:30-37`).

### Concerns
- **HIGH — a DLR `failed` write creates an infinite resend loop.** `dispatcher.ts:129-135` selects `status in ("pending","failed")` with `next_retry_at <= now`. On a `sent` row, `next_retry_at` is the original creation time, so writing `failed` (as the plan prescribes) makes the row immediately eligible again, without incrementing `retry_count` and without backoff. Meta-rejected sends (invalid number) would be retried forever by the cron in `app/api/cron/dispatch-communications/route.ts:18`, each attempt billable. `failed` in this codebase means *retryable* (`dispatcher.ts:255-269`), so D-06's "permanent failure → `failed`" contradicts the state machine.
- **HIGH — `category: "communication"` violates a CHECK constraint.** Plan 02 Task 3 inserts a failed-delivery notification with `category: "communication"`, but `000014:97` allows only `('clinical','queue','billing','system')`. Every urgent DLR failure alert will throw at insert time (silently, since the plan does not check the error).
- **HIGH — inbound action resolution can cancel the wrong clinic's appointment, or cancel on a numeric text.** `findActiveAppointmentByPhone` does a *global* `ilike("phone", '%<last10>%')` across all tenants and takes `.limit(1)` (`features/appointments/actions.ts:306-325`). With one centralized WABA (D-02) serving every clinic, a patient of two clinics gets an arbitrary tenant's appointment; substring matching also matches numbers that merely contain the 10 digits. Compounding this, `parseInboundAction` treats bare `"2"` as **cancel** and `"no"` as **cancel** (`lib/messaging/webhook-helpers.ts:52-59`), so a patient answering "2 days" to a free-text question triggers immediate cancellation with slot release. Plan 02 keeps both behaviors and makes them production-live.
- **HIGH — DLR status can regress and lose metadata.** The plan does read-modify-write of `metadata` from a previously selected row and applies no ordering guard, so a late `Delivered` after `Read` downgrades `read` → `delivered` and can drop `read_at`; two concurrent events race the merge.
- **MEDIUM — missing-`requestId` guard.** Some MSG91 events (e.g. `Sent`/`Submitted`) may lack `request_id`; `eq("external_message_id", undefined)` yields a PostgREST error. The plan's branch returns 200 only if the lookup path is defensive; nothing in the tasks defines the guard.
- **MEDIUM — no webhook idempotency / dedup.** MSG91 retries failed webhooks. Duplicate `Delivered` = duplicate audit rows; duplicate button replies = duplicate "confirmed" audit and a second ack. Nothing keys on `message_uuid`/`uuid` (`route.ts` currently has no dedup either).
- **MEDIUM — webhook work is done inline within MSG91's response window.** The branch does 2–4 Supabase round-trips plus an outbound WhatsApp send before responding; the plan asserts "<5s" as an acceptance item but provides no mechanism (queue/short-circuit) if MSG91 is slow. AGENTS.md §20 pushes this to a job.
- **MEDIUM — `.env.example` not updated.** `MSG91_WEBHOOK_SECRET` is now required in production but appears nowhere in `.env.example` (only `MSG91_AUTH_KEY`, `MSG91_INTEGRATED_NUMBER`, `MESSAGING_PROVIDER`). Also, the plan's "if neither secret configured → dev bypass" rule means a production deploy that forgets `MSG91_WEBHOOK_SECRET` while `MSG91_AUTH_KEY` is set is fine, but the inverse ordering must be spelled out or a mis-set secret silently 403s all inbound.
- **MEDIUM — non-catalogue acks depend on the 24h window.** `appointment_confirmed_ack`, `appointment_cancelled_ack`, `appointment_reschedule_link`, `conversational_triage`, `bot_not_found` are not in `whatsapp-templates.json` (verified: 13 templates, none of these). Sending them via the session text endpoint only works while the window is open; the plan handles this only for tone ("silently log") in research, not as a task.
- **LOW — `appointment_reminder` is never enqueued anywhere** (grep across `features/`, `lib/`, `app/`), so the plan's "urgent failure → receptionist alert for reminders" branch is currently dead code, and 17-of-13... rather, several catalogued templates (`follow_up_due`, `pediatric_vaccine_due`, `balance_due_reminder`) have no producer either.
- **LOW — route signature change ripples.** `verifyWebhookSignature` gains a 4th param; existing callers/tests (`tests/messaging/two-way-bot.spec.ts:28,36,45`) pass 3 args — fine because optional, but the plan should state the default behavior when `searchParams` is omitted.

### Suggestions
1. Give DLR failures a terminal state distinct from retryable failure: either `dead_letter`, or add `terminal_failure`/`undeliverable` to the check constraint in `000016` **and** exclude it from `dispatchPendingQueue` (`dispatcher.ts:132`). Also set `next_retry_at` far future as belt-and-braces.
2. Change the alert insert to `category: "system"` (or `"queue"`) and check `error` from every insert; add a test that asserts the insert payload against the DB enum.
3. Make action resolution authoritative, not textual: correlate the inbound message to the *outbound* message via `replyMsgId`/`requestId` → `communication_queue.tenant_id`+`appointment_id`, and require the tenant to be derived from that row. Restrict `cancel`/`reschedule`/`confirm` to `button_reply.id` only; treat all free text (including "1"/"2"/"yes"/"no") as triage. Add a test with two tenants sharing a phone number.
4. Implement status transitions monotonically: `sent < delivered < read`, ignore regressions; merge `metadata` via a SQL JSONB expression or `metadata || $1` as part of the same update rather than read-then-write.
5. Add a dedup table or a `metadata`-keyed guard on `message_uuid` for DLR and on inbound `replyMsgId` for button actions; add tests that replay the same webhook twice.
6. Add `MSG91_WEBHOOK_SECRET=` to `.env.example` and document the 403-on-mismatch behavior.

### Risk Assessment
**HIGH.** Two of the findings (DLR `failed` → cron resend loop; `category: "communication"` constraint violation) are certain runtime failures, and one (global phone match + numeric-text cancel) can cancel the wrong patient's appointment — the worst possible failure mode for this product. The plan's tests are structured around mocked happy paths and would not surface any of them.

3. Write `mapRemoteStatuses` to accept `status` case-insensitively and read `template_name || name`, `id || template_id`, and both `data` and `data.templates` shapes; add fixtures for each.

5. Add `--status` to the manual verification table alongside the existing approval row (`05.1-VALIDATION.md:65`).

**MEDIUM.** The plan will not break production, but its main deliverable is a status reporter whose failure mode is "everything looks NOT SUBMITTED", and its test seam is blocked by an unguarded `main()`. Both are cheap to fix before execution.

**Shared blind spots across all three plans:**
1. **Config surface.** No plan touches `.env.example` or documents `MSG91_INTEGRATED_NUMBER`/`MSG91_WEBHOOK_SECRET` wiring, though all three depend on it. AGENTS.md §32 requires configuration documentation.
2. **Existing outbox semantics.** None of the plans reconcile the new DLR statuses with `dispatchPendingQueue`'s selection (`dispatcher.ts:129-135`) or its existing SMS fallback enqueue (`dispatcher.ts:271-293`), which uses `${message_type}_sms_fallback` template IDs that exist nowhere in the repo — with D-01 deferring SMS, every WhatsApp failure will enqueue a guaranteed-failing SMS attempt.
3. **Success-criteria mismatch (governance).** The roadmap's criteria 4 (SMS Flow/DLT) and 5 (SendOTP/VerifyOTP) cannot be met by these plans because D-01 defers them; criterion 6 (`docstar-cli`, `https://mcp.msg91.com/mcp`) is referenced only in `05.1-CONTEXT.md:51,76` and `05.1-RESEARCH.md:367-380` and has **no task, no dependency, and no verification** in any of the three plans. Either the roadmap criteria must be amended to "deferred" or a fourth plan is missing. As written, phase verification will fail on criteria 4–6 regardless of execution quality.
4. **Verification breadth.** All plans verify with `vitest` + `tsc` only. AGENTS.md §28 asks for lint and a build check on changed routes/providers; `npm run lint` is absent from every verify block.
5. **Asynchronous work.** D-04/D-05/D-06 all perform external I/O inside the webhook request (Supabase writes + outbound sends), against AGENTS.md §20's preference for jobs.

## Overall Risk Assessment

**HIGH.**

The plans are well-structured, correctly scoped to WhatsApp, correctly identify the broken provider, and correctly reuse the existing cancellation domain logic. But the quality of the mapping matrix is asserted rather than derived from callers, and four templates plus one production-blocking env var would ship visibly wrong patient messages on day one. Wave 2 contains two certain runtime defects (retry loop on DLR failure, `category` CHECK violation) and one severe correctness/security gap (global phone→appointment resolution, combined with numeric-text cancellation) that the existing test style — mocked single-tenant happy paths — will not catch. None of the plans can satisfy the roadmap's success criteria 4–6 until the roadmap is amended or a fourth plan is added.

Highest-leverage fixes before execution, in order: (1) resolve inbound action via `replyMsgId` → queue item (tenant-scoped), and stop treating free text as cancel; (2) make DLR failure terminal and fix the `category` enum; (3) read `MSG91_INTEGRATED_NUMBER` in the provider; (4) derive the alias table from real `enqueueMessage` call sites, including `prescription_url`/`receipt_url` for `consultation_documents`; (5) reconcile the roadmap criteria with D-01.
