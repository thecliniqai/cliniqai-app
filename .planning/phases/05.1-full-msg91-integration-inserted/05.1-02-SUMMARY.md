## 1. Executive Summary

Wave 2 of Phase 05.1 implemented the bidirectional communications foundation for ClinicOS:
1. **Interactive Two-Way WhatsApp Bot Actions (Decision D-04):** Enabled instant patient actions from WhatsApp quick-reply buttons (`[Confirm]`, `[Cancel]`, `[Reschedule]`), triggering immediate doctor calendar slot release and waitlist notifications on cancellation with `cancellation_reason: "patient_whatsapp_bot"`.
2. **Conversational Auto-Triage (Decision D-05):** Unhandled queries and conversational replies trigger an automated polite reply and fire Event #18 `inbound_whatsapp_reply` in-app notifications with `category: "system"` to the front-desk queue.
3. **Delivery Reports (DLR) Lifecycle Tracking (Decision D-06):** Inbound status webhooks from MSG91 capture delivery states (`delivered`, `read`, `failed`), updating the outbox queue (`communication_queue`) with monotonic status progression and logging audit entries.
4. **Cross-AI Peer Review Hardening:**
   - **Gated Cancellation (Finding 5):** Cancellation with calendar slot release is strictly restricted to interactive quick-reply button clicks (`btn_cancel`), routing loose numeric/free-text replies (`"2"`, `"no"`, `"2 days"`) to conversational auto-triage.
   - **Multi-Tenant Message Correlation (Finding 5):** Inbound button replies resolve tenant context and appointment ID via `replyMsgId` / `external_message_id` outbox correlation, eliminating cross-tenant cancellation risk.
   - **Dead-Letter State Transition (Finding 3):** Permanent delivery failures transition `communication_queue` status to `dead_letter` and clear `next_retry_at`, preventing infinite retry loops in `dispatchPendingQueue`.
   - **Notification Category CHECK Constraint (Finding 4):** Delivery failure and triage notifications use valid category `'system'` adhering to PostgreSQL constraint `000014:97`.

## 4. Key Design Decisions & Security Mitigations

1. **Cancellation Guard & Accidental Slot Release Prevention:**
   Free text such as `"2"`, `"no"`, or `"2 days"` no longer triggers appointment cancellation. Cancellation strictly requires an explicit button reply identifier (`btn_cancel`, `cancel:*`, or `isButtonClicked && action === "cancel"`). Loose free text is safely routed to conversational triage.
2. **Tenant-Scoped Message Correlation:**
   Incoming replies containing `replyMsgId` are correlated against `communication_queue.external_message_id`. This extracts both the exact `tenant_id` and `appointment_id`, ensuring a patient registered across multiple clinics can never accidentally cancel or confirm a visit at the wrong clinic.
3. **DLR Monotonic Status Progression:**
   When a late `Delivered` DLR arrives after a `Read` DLR, `communication_queue.status` remains `"read"` to prevent status regression.
4. **Dead-Letter State on DLR Delivery Failures:**
   Permanent delivery failures transition `communication_queue.status` to `"dead_letter"`, clear `next_retry_at` to `null`, and record `error_message`. This prevents `dispatchPendingQueue` cron jobs from repeatedly attempting to redeliver unserviceable numbers.
5. **PostgreSQL Constraint Adherence:**
   All `in_app_notifications` inserts for missed reminders, failed deliveries, and auto-triage strictly use `category: "system"`, adhering to PostgreSQL constraint `000014:97` (`clinical`, `queue`, `billing`, `system`).
