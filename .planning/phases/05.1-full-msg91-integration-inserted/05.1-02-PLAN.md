    1. Enhance `verifyWebhookSignature`:
       - Add support for checking query parameters (`searchParams?: URLSearchParams`):
         ```typescript
         export function verifyWebhookSignature(
           provider: string,
           headers: Headers,
           rawBody: string,
           searchParams?: URLSearchParams
         ): boolean
         ```
       - For `provider === "msg91"`:
         - Check header `authkey` against `process.env.MSG91_AUTH_KEY`.
         - Check query param `secret` or header `x-webhook-secret` against `process.env.MSG91_WEBHOOK_SECRET`.
         - If either match matches expected secret, return `true`.
         - If neither `MSG91_AUTH_KEY` nor `MSG91_WEBHOOK_SECRET` are configured:
           - In non-production (`process.env.NODE_ENV !== "production"`), return `true` (enables local test execution).
           - In production, return `false`.
    2. Update `parseInboundAction(body: string, isButtonClicked = false)` (Cross-AI Review Finding 5):
       - Restrict `"cancel"` strictly to interactive button clicks (`isButtonClicked && (id === "btn_cancel" || body.startsWith("cancel:"))`).
       - Restrict `"confirm"` to interactive button `btn_confirm` or affirmative keywords with appointment context.
       - For all general free-text (including `"2"`, `"no"`, or general text without explicit button click), return `"unhandled"` to ensure conversational triage and front-desk notification without accidental slot cancellation.
    3. Add `parseMsg91Payload(rawBody: string, searchParams?: URLSearchParams)`:
       - Safely parses JSON body or query string.
       - Returns a discriminated union:
         ```typescript
         export type Msg91WebhookEvent = 
           | {
               type: "dlr";
               status: "delivered" | "read" | "failed" | "other";
               rawStatus: string;
               requestId: string;
               customerNumber: string;
               deliveredAt?: string;
               readAt?: string;
               reason?: string;
             }
           | {
               type: "inbound";
               from: string;
               body: string;
               buttonId?: string;
               replyMsgId?: string;
               action: "confirm" | "cancel" | "reschedule" | "unhandled";
               rawPayload: unknown;
             };
         ```
       - **DLR detection logic:**
         - Checks if `direction === "outbound"` OR `status` in `["Delivered", "Read", "Failed", "Send", "Submitted", "delivered", "read", "failed"]` OR `eventName` contains `"Event"`.
         - Maps `status` to `"delivered" | "read" | "failed" | "other"`.
         - Normalizes `requestId` from `request_id || requestId || message_uuid`.
       - **Inbound extraction logic:**
         - Resolves `from` / `customerNumber` (cleans leading `+` and non-digits).
         - Resolves interactive reply:
           - If `interactive` string exists: `JSON.parse` to extract `button_reply.id` and `button_reply.title`.
           - If `button` string exists: `JSON.parse` to extract `text` or `payload`.
           - Extracts `replyMsgId` or context message ID if present for message correlation.
           - If `text` exists: uses raw text.
         - Calls `parseInboundAction(body, isButtonClicked)` to categorize into `"confirm" | "cancel" | "reschedule" | "unhandled"`.
  </action>

           - For `status === "delivered"`:
             - If existing `queueItem.status === "read"`, keep status as `"read"` (monotonic progression, do not downgrade).

               `metadata: { ...queueItem.metadata, delivered_at: deliveredAt || new Date().toISOString() }`
             - Insert into `audit_logs`: `action: "communication_dlr_delivered"`, `tenant_id: queueItem.tenant_id`, `entity_type: "communication_queue"`, `entity_id: queueItem.id`.
           - For `status === "read"`:
             - Update `communication_queue`:
               `status: "read"`, `metadata: { ...queueItem.metadata, read_at: readAt || new Date().toISOString() }`
             - Insert into `audit_logs`: `action: "communication_dlr_read"`.
           - For `status === "failed"` (Cross-AI Review Finding 3):
             - Transition to `"dead_letter"` and clear `next_retry_at` to prevent `dispatchPendingQueue` infinite resend loops:
               `status: "dead_letter"`, `next_retry_at: null`, `error_message: reason || "Delivery failed"`.
             - Insert into `audit_logs`: `action: "communication_dlr_failed"`.
             - If `queueItem.message_type` is an urgent clinical notification (`appointment_booked`, `appointment_rescheduled`, `appointment_reminder`):
               - Insert into `in_app_notifications` with valid category `"system"` (Cross-AI Review Finding 4):

Reason: ${reason || "Unreachable"}`.
         - Return `NextResponse.json({ success: true, event: "dlr_processed", status })`.
       - **Branch B: Inbound Customer Interaction (Cross-AI Review Finding 5):**

         - `unhandled`: Notify front desk with Event #18 `inbound_whatsapp_reply` (`category: "system"`), send `conversational_triage` polite reply.
