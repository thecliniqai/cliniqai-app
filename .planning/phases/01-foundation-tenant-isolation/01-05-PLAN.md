  <behavior>
    - For each tenant-owned table, a session authenticated in tenant A reads zero rows owned by tenant B.
    - A session authenticated in tenant A attempting to write to tenant B's rows changes nothing and is refused.
    - A forged tenant_id sent in a payload or query filter returns only the caller's own rows.
    - A user with memberships in both tenants sees only the active tenant's rows per request.
    - Consecutive-page reads with tied created_at values neither repeat nor drop rows.
    - Every tenant-owned table reports RLS enabled with at least one policy and no USING(true) tenant policy.
  </behavior>
  <action>
    Turn "we set up RLS" into evidence.

    (1) `tests/helpers/tenants.ts`: extend the seeding helper to build two independent tenants (A and B), each with its own owner plus a staff member, plus one user who is a member of BOTH tenants with distinct roles. Seed representative rows per table per tenant (patients, consent records, audit rows, invitations, subscriptions, payment records) through the service-role admin client, and return authenticated (anon-key, cookie-bound) clients per actor so tests act as real sessions rather than as the service role.

    (2) `tests/helpers/rls.ts`: catalog-level assertions against the live project — enumerate tenant-owned tables via `information_schema`/`pg_class`, assert `relrowsecurity` is true for each, assert each has at least one policy in `pg_policies`, and assert no tenant-scoped policy is written as an unconditional `USING (true)` grant on a tenant-owned table. Keep the expected table list explicit (the eight tenant-owned tables plus any added later) so a new table without a policy entry fails the assertion rather than being silently skipped; write the failure message so a future reader knows exactly which table and which policy is wrong.

    (3) `tests/security/cross-tenant.spec.ts`: the matrix. For each tenant-owned table and each of read and write, exercise tenant A's session against tenant B's rows and assert zero-effect (read returns nothing; write is refused and leaves tenant B's row unchanged when re-read with the service role). Then the client-supplied-tenant attack: send tenant B's identifier in a payload field and as a query filter while authenticated in tenant A, and assert the result is identical to omitting it — this is the concrete test behind the "never trust a browser-supplied tenant id" rule. Then the dual-membership case: the same user acting with tenant A active sees zero tenant B rows, and the explicit selection-required path (from Plan 02) is exercised rather than defaulting to an arbitrary tenant. Then pagination stability: seed more rows than fit one page with deliberately tied `created_at` values, walk every page, and assert the union equals the seeded set exactly, in deterministic order, with no repeats or gaps.
