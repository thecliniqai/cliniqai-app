## Checked and found sound

- Migration 000112: the actor and active-tenant guard, `consultations:edit`, claim before locks (a rolled-back conflict or lock leaves no claim), visit `FOR NO KEY UPDATE` then notes `FOR UPDATE`, `DRAFT_LOCKED` covering sealed and unsigned completed or cancelled visits while allowing the amending state, version compare under the locks, grants (`authenticated` only, revoked from PUBLIC, anon and service_role), definer helpers with no API grant, audit through `log_command_audit` with allow-list parity (SQL and `AUDIT_ACTIONS` and `COMMAND_ONLY_AUDIT_ACTIONS`). The version trigger fires after `clinical_notes_guard` and there is no later BEFORE UPDATE trigger on the table. The grant narrowing is consistent with the remaining writers: I grepped `follow_ups` and `clinical_notes` writes under `features`, `lib` and `app` and only the vitals recorder (`updateClinicalNotes`) and the command remain.
- Migration 000113 and 000114: INVOKER, STABLE, `search_path = ''`, `has_permission(p_tenant_id, ...)` gate, doctor-own scoping (`doctor_id = auth.uid()`), LIKE escaping, signed-only history with the current visit excluded, no patient or visit ids in `consult_assist_context`. `pg_trgm` is resolved by schema through `quote_ident`.
- Migration 000115: tenant FK and composite doctor FK (the same RESTRICT precedent as 000049), RLS on all four operations with `consultations:edit` and `doctor_id = auth.uid()`, grants without anon, insert trigger forcing `doctor_id`, 200-row cap under an advisory lock, immutable identity columns. The macros service passes `tenantId` and `userId` from the session, never from input.
- `app/api/ready/expected-migration.ts` is `000115` at HEAD and each migration commit touched it (`2e27820b`, `a3d6ffe8`, `85293602`, `c3828d3d`).
- The new routes and actions all authenticate and take the tenant from the session: `saveConsultationDraft` (`consultations:edit`), `getConsultationDraft` (`consultations:view`, uuid-checked), `GET /api/terminology/diagnoses` (`consultations:view`, mapped refusal codes, `no-store`, entitlement resolved server-side), the macro actions, and the page (`hasPerm` plus the RLS-filtered visit read).
- Sealed records: the draft command refuses sealed visits itself and the 09A guards still fire. The workspace derives `readOnly` from `recordState` and the 09A specs keep their assertions with changed selectors only. I found no new write path to sealed clinical rows.
- Saver logic (`draft-saver.ts`): one request in flight, edits during a save go to the next one, a retry reuses the same id and payload, an unknown outcome keeps the attempt and a definite refusal drops it, rebase is field by field with an explicit prompt on overlap, and Sign, Finalize and Finish wait on `flush()` (a conflict or lock blocks them). `rebaseDraft` is a correct three-way merge.
- Today follow-up reads and the open-amendments read run on the user's own client under RLS and are gated by permission.
- Tests I sampled assert real outcomes (rows, versions, DOM state, fault injection with a control run), for example the B-5 test that now checks the notes are unchanged after a failed follow-up write.
