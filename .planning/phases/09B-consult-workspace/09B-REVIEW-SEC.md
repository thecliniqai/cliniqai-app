# 09B — adversarial security review (static)

Scope: `git diff f15fa252f5452351366cc641250bf12166f3e776..HEAD` on `v2/phase-09b-consult-workspace` (migrations 000112–000115, the
diagnosis-search route, macros, snapshot / Smart Assist reads, follow-up display, upload path, `next.config.ts`). Static review only: code and SQL
read, `git` / `grep` run, nothing executed against any database. The attacker is an authenticated member of the clinic (any role), a member of
another clinic, a former member, or anyone on the internet for pre-authentication paths, calling actions, routes and PostgREST/RPC directly.

No Critical or High finding. The definer command, the three INVOKER reads and the macro table hold against cross-tenant, cross-doctor,
former-member and role attacks.

## Attacked and found sound

**`save_consultation_draft` (000112)**
- SECURITY DEFINER with `search_path = ''`, qualified names, and `lock_timeout 2s`. EXECUTE goes to `authenticated` only (revoked from PUBLIC, anon and service_role). The shared step, the version-bump trigger function and `log_command_audit` have no API grant.
- Tenant: `p_tenant_id` must equal `authz.full_tenant_ids()`, which requires an active membership, the active clinic and a `full` clinic. A forged tenant, another clinic, a removed or suspended member and a locked clinic all get VISIT_NOT_FOUND. The visit and the notes row are looked up with `tenant_id = p_tenant_id`, so another clinic's visit id is not found.
- Permission: `has_permission(..., 'consultations:edit')` (owner, doctor). Nurse, receptionist and admin get FORBIDDEN. The visit is started only when the caller also holds appointments:edit.
- Seal: the visit is locked FOR NO KEY UPDATE and the notes row FOR UPDATE, then a sealed, completed or cancelled visit is refused (DRAFT_LOCKED). The 09A guards still fire inside the definer body because `auth.uid()` is set (`clinical_notes_guard`, the follow-ups guard). The trigger order (`clinical_notes_guard` < `clinical_notes_version_bump`) means a refused write bumps nothing, and the guard's vitals-only comparison sees the old `draft_version`.
- `draft_version` is set by the trigger on every path. The column grant is `(vitals)` only, so a caller cannot write the version.
- Idempotency: `command_claim` keys (tenant, request id) and compares the command, actor and request hash (visit, version, patch). Another user's request id gives IDEMPOTENCY_MISMATCH. The claim rolls back with a DRAFT_LOCKED / DRAFT_CONFLICT refusal.
- Patch key allow-list, types, the 256 kB bound, provenance limited to the two AI keys, and `recorded_by` stripped and re-derived (inside the command).
- Follow-ups: there is one per visit (partial unique index, upsert). The patient comes from the visit row and the doctor from `auth.uid()`, never from the caller. No message or job is enqueued (no follow-up reminder job exists). INSERT/UPDATE/DELETE on `follow_ups` are revoked from `authenticated`, and no request-path writer remains (grep).
- The audit metadata holds field names, the version and a boolean only, so no PHI. `consultation.draft_save` is now refused by `log_audit` (command-only), so a member cannot forge one.

**`consult_assist_context` (000113)**: INVOKER, so RLS applies. It reads only `visits.doctor_id = auth.uid()`, signed visits, and returns names and counts with no patient or visit ids. Without consultations:edit in the active clinic, or with a forged tenant, the result is empty. No unsigned drafts. It is called only from the server page with the session tenant.

**`search_diagnoses` (000114)**: INVOKER and consultations:view. Custom rows are limited to `doctor_id = auth.uid()` (another doctor's custom diagnoses never appear, even though the table policy would show them). At most 8 terms of at most 100 characters, and `\`, `%`, `_` are escaped against LIKE's default escape. `p_limit` is clamped to 1–50 and `p_specialty` is bound as a parameter. The pg_trgm schema is resolved once at migration time and quoted.

**`patient_snapshot` (000114)**: INVOKER and consultations:view. The patient must be in `p_tenant_id`, not deleted and not erased. It uses signed visits only (no drafts or unsigned notes). Rx lines come from the signed header only and are still filtered by `prescriptions:view` RLS (a nurse sees none). Follow-ups are filtered by `appointments:view` RLS, and vitals carry no recorder id. A receptionist gets NULL.

**`doctor_text_macros` (000115)**: RLS on all four operations requires `consultations:edit` in the active clinic **and** `doctor_id = auth.uid()`. A forged `doctor_id` is overwritten by the BEFORE INSERT trigger, and the WITH CHECK holds by construction. UPDATE cannot move a row's id, tenant or doctor. A colleague, the owner, a nurse, another clinic and a former member (via `full_tenant_ids` `status = 'active'`) see nothing. The 200-macro cap is serialised by an advisory lock. Grants go to `authenticated` only (none to anon). The composite FK to memberships uses RESTRICT, the same as the other own-row tables. Macro text is never logged. Expansion is a single pass with `hasOwnProperty`, so there is no recursion or prototype key, and React escapes the rendering.

**`GET /api/terminology/diagnoses`**: `resolveServiceContext("consultations:view")` runs before the input is read, and the tenant and doctor come from the session. Error bodies are fixed text, and `Cache-Control: private, no-store` is set on every response. Control characters are stripped, length is capped at 100, and `specialty` is checked against an allow-list. It uses the user's JWT client with no service role. The entitlement is resolved from the session. There are no CORS headers, and the GET has no side effects.

**Macros actions, `getConsultationDraft`, `getConsultAssistContext`, `getPatientSnapshot`, `getUpcomingVisitInstants`, `getOpenAmendments`, the Today follow-up read**: each authenticates and checks permission first (or is server-only and reached with a resolved context), filters on `ctx.tenantId`, runs under RLS, validates ids as UUIDs, and answers failures with fixed text or null.

**Follow-up booking (consult "Book follow-up" and the front-desk Today button)**: neither adds a writer. Both open the V2-08 booking sheet, whose `create_visit` command applies the tenant, patient and permission checks. A double booking is a business concern of that command, not a new path.

**Uploads**: `labs:edit` is checked before input. The patient must be in the clinic, and the visit must be in the clinic and belong to that patient. The storage key is made of ids only (`tenants/<t>/patients/<p>/labs/<uuid>.<[a-z0-9]{1,10}>`), so there is no path traversal. `upsert: false`. The type and the 25 MB size are checked on the server (`labFileRefusal`), not only on the client. Signed links last 5 minutes, and `isPatientStoragePath` is rechecked. Rows are append-only.

**Service-role client**: no file changed in this phase acquires `lib/supabase/system.ts` or a service key on a request path (grep over the non-test diff).

**PHI in logs, errors and bundles**: the new `log.*` lines carry the event, error tag, request id and tenant id only. `reportClientError` is development-only and prints an error tag. The draft lives only in memory (no Web Storage, IndexedDB or Cache Storage writes in the saver or hook). The service worker does not cache `/api` or action POSTs. The validation error summary carries paths and messages, not values. `ConsultDocument` strips the storage path and the uploader.
