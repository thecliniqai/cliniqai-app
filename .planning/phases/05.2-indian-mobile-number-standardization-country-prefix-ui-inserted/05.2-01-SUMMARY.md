## 1. Executive Summary

Wave 1 of Phase 05.2 establishes the foundational domain, database, and validation layer for Indian mobile phone number standardization conforming to the Indian National Numbering Plan (NNP) and international ITU-T E.164 persistence standards.

All 3 planned tasks were executed test-first and committed atomically:
1. **Core Indian Phone Utility & Unit Test Suite (`lib/utils/phone.ts`, `tests/utils/phone.spec.ts`):** Created centralized phone utility providing `INDIAN_MOBILE_REGEX = /^[6-9]\d{9}$/`, `extractTenDigits()`, `toE164()`, `isValidIndianMobile()`, and `formatTenDigitsDisplay()`. Established a 24-test unit test suite covering 10-digit formats, prefixed strings (+91, 91, 0), formatted strings, landline/invalid prefixes (0–5), partial strings, and null/undefined handling.
2. **Idempotent Database Migration (`supabase/migrations/000017_normalize_indian_phone_numbers.sql`):** Created PL/pgSQL function `normalize_indian_phone_e164` that cleans non-digits, trims leading 91 or 0 prefixes, and outputs `+91XXXXXXXXXX` for valid 10-digit subscriber numbers starting with 6–9. Added defensive, conditional update blocks targeting `patients` (`phone`, `guardian_phone`), `staff_members` / `memberships` (`phone`), `clinics` / `tenants` (`phone`), and `communication_queue` (`recipient_phone`).
3. **Schema Boundary Validation & Deduplication Hardening (`features/patients/schema.ts`, `features/settings/schema.ts`, `features/patients/dedup.ts`, `tests/patients/schema.spec.ts`):** Upgraded `patientSchema.phone` to strictly enforce 10-digit Indian mobile numbers starting with 6–9 and transform them to E.164 (`+91XXXXXXXXXX`). Refactored `normalizePhone` to delegate to `toE164`. Added `optionalIndianPhone` to `features/settings/schema.ts` for clinic `doctor_phone`, user profile `phone`, and staff `phone`. Hardened `findPotentialDuplicates` in `dedup.ts` to normalize phone numbers with `toE164` before executing tenant-scoped exact match queries.

## 4. Key Design Decisions & Deviations

1. **Preserving `undefined` in `optionalIndianPhone` (Deviation):** In `features/settings/schema.ts`, `optionalIndianPhone` was initially returning `null` for falsy values. Because forms like `clinic-profile-form.tsx` submit `{ doctor_phone: ownerIsPracticing ? doctorPhone : undefined }`, `optionalIndianPhone` was adjusted to preserve `undefined` when `undefined` is provided, while mapping empty strings or `null` to `null`. This prevents TypeScript type mismatch between input and output shapes while keeping validation strict.
2. **Defensive Multi-Schema Target in Migration 000017 (Enhancement):** The PostgreSQL migration targets both logical conceptual table names (`staff_members`, `clinics`) and physical schema tables (`memberships`, `tenants`, `patients.guardian_phone`) using `information_schema.columns` inspection. This ensures zero migration errors regardless of deployment environment or staging state.
3. **Backwards-Compatible `normalizePhone` Delegation:** Refactored `features/patients/schema.ts`'s `normalizePhone` to call `toE164(phone)`, preserving backwards compatibility across external call sites and legacy tests while ensuring centralized logic.
